## Service Level Objectives

*[Book, Part II - Principles, Chapter 4](https://sre.google/sre-book/service-level-objectives/)*

### Service Level Terminology

**SLI (Service Level Indicator)** — a quantitative measure of some aspect of the level of service provided. Common SLIs:

- **Latency** — time to return a response
- **Error rate** — fraction of failed requests
- **Throughput** — requests per second
- **Availability** — fraction of time the service is usable (often measured as *yield*: fraction of successful requests)

Availability is expressed in "nines": 99% = "two nines", 99.95% = "three and a half nines", 99.999% = "five nines".

See: [Availability Table](https://sre.google/sre-book/availability-table/).

**SLO (Service Level Objective)** — a target value or range for an SLI.

- Example: *99% of Get RPCs complete in < 100 ms*.
- Multiple targets can describe the shape of the distribution (e.g. p90 < 1 ms, p99 < 10 ms, p99.9 < 100 ms).
- It is better to allow an **error budget** (rate at which the SLO can be missed) than to aim for 100%.

**SLA (Service Level Agreement)** — a contract with users that includes consequences (financial or otherwise) for missing the SLOs it contains.

- If there is no explicit consequence, it's an SLO, not an SLA.
- SRE helps define SLIs and avoid triggering SLA consequences, but SLAs are business/legal decisions.

### Indicators in Practice

**Choose SLIs by system type:**


| System type          | Key SLIs                          |
| -------------------- | --------------------------------- |
| User-facing serving  | Availability, latency, throughput |
| Storage              | Latency, availability, durability |
| Big data / pipelines | Throughput, end-to-end latency    |
| All systems          | Correctness                       |


**Collection:** prefer client-side instrumentation when possible; server-side metrics can miss problems the user actually experiences (e.g. slow JavaScript).

**Aggregation:** use **percentiles** (p50, p95, p99) instead of averages — averages hide tail latency. Users prefer a slightly slower system over one with high variance.

**Standardize:** create reusable SLI templates (measurement method, aggregation interval, which requests are included) so definitions are consistent across services.

### Objectives in Practice

- Start from what users care about, then work backward to measurable indicators.
- Specify how SLOs are measured and under which conditions they are valid.
- For heterogeneous workloads, define separate objectives per class.

**Choosing targets:**

1. Don't lock into current performance — it may require heroic effort to sustain.
2. Keep it simple — complex aggregations obscure changes.
3. Avoid absolutes — "always available" or "infinite scale" is unrealistic.
4. Have as few SLOs as possible — if you can't win a priority argument by quoting it, drop it.
5. Perfection can wait — start loose, tighten over time.
Remember — "If you can’t ever win a conversation about SLOs, it’s probably not worth having an SRE team for the product."

**Control loop:** Monitor SLIs → Compare to SLOs → Decide if action is needed → Take action.

**Setting expectations:**

- Keep a **safety margin**: internal SLO tighter than the external one.
- **Don't overachieve**: users rely on actual performance, not stated SLOs. Deliberately introduce planned outages or throttling to prevent over-dependence (e.g. Google Chubby's planned outages).

### Agreements in Practice

- Be conservative in what you advertise — SLAs are hard to change once published.
- SRE's role: help business/legal understand the likelihood of meeting the SLOs inside the SLA.

## Implementing SLOs

*[Workbook, Part I - Foundations, Chapter 2](https://sre.google/workbook/implementing-slos/)*

### Why SREs Need SLOs

- SLOs drive prioritization: they let you calculate the **opportunity cost** of reliability work vs. feature work.
- Without SLOs, there is no objective basis for an SRE team to exist.
- Day-to-day SRE work = defending SLOs short-term and making them sustainable long-term.

### Getting Started

**Prerequisite state for error-budget-based SRE:**

1. All stakeholders approved the SLOs as fit for the product.
2. The team responsible agrees the SLO is achievable under normal circumstances.
3. The org committed to using the error budget for decision-making (formalized in an error budget policy).
4. There is a process to refine the SLOs over time.

**Why 100% is the wrong target:**

- Leaves no room for anything other than reactive work.
- Change is the #1 source of outages — no changes means a stagnant product.
- The chain between you and the user always has components that can fail.
- Each extra "nine" costs more but gives diminishing marginal utility to users.

### What to Measure: Using SLIs

Express SLIs as a ratio: `good events / total events` (range 0–100%).

- This maps naturally to error budgets: `error budget = 100% - SLO`.
- Example: 99.9% SLO over 3M requests → budget of 3,000 errors.

Distinguish **SLI specification** (what matters, independent of measurement) from **SLI implementation** (how you actually measure it). A single spec can have multiple implementations with different quality/coverage/cost tradeoffs.

In the first book, it is advised against picking an SLO based upon current performance, because this can commit you to unnecessarily strict SLOs. While that advice is true, your current performance can be a good place to start if you don’t have any other information, and if you have a good process for iterating in place (keep in mind that if your service returns successful requests 99.999% of the time in less than 10 ms, any significant regression from that baseline may make the users unhappy).

**How to start**
Having trouble figuring out what sort of SLIs to start with? Start simple:

- Choose one application for which you want to define SLOs.
- Decide clearly who the “users” are in this situation. Optimize their happiness.
- Consider the common ways your users interact with your system—common tasks and critical activities.
- Draw a high-level architecture diagram of your system; show the key components, the request flow, the data flow, and the critical dependencies. Group these components into categories listed in the following section (there may be some overlap and ambiguity; use your intuition and don’t let perfect be the enemy of the good).
- Think carefully about your SLIs, but don’t overcomplicate things. Especially if you’re just starting your SLI journey, pick an aspect of your system that’s relevant but easy to measure—you can always iterate and refine later.

**SLIs by component type:**


| Component      | SLI types                        |
| -------------- | -------------------------------- |
| Request-driven | Availability, latency, quality   |
| Pipeline       | Freshness, correctness, coverage |
| Storage        | Durability                       |


### Moving from Specification to Implementation

Pick the cheapest viable data source first (logs > probes > client instrumentation).

**Sources ranked by closeness to user:**

1. Client-side instrumentation (best quality, highest cost)
2. Load balancer monitoring
3. Application server logs
4. Black-box monitoring

**Measuring with Prometheus (example):**

```promql
# Availability (7-day window)
sum(rate(http_requests_total{host="api", status!~"5.."}[7d]))
  / sum(rate(http_requests_total{host="api"}[7d]))

# Latency percentiles
histogram_quantile(0.9, rate(http_request_duration_seconds_bucket[7d]))
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[7d]))
```

Round down measured SLIs to get **starter SLOs** (e.g. 97.123% → 97% availability).

### Choosing a Time Window


| Window type                   | Pros                                                           | Cons                                       |
| ----------------------------- | -------------------------------------------------------------- | ------------------------------------------ |
| **Rolling** (e.g. 4 weeks)    | Aligns with user experience; no "forgetting" at month boundary | —                                          |
| **Calendar** (e.g. quarterly) | Aligns with business planning                                  | Mid-period uncertainty on remaining budget |
| **Short** (weekly)            | Fast course-correction                                         | Not enough data for strategic decisions    |
| **Long** (quarterly)          | Good for large project decisions                               | Slow to react                              |


Recommendation: **4-week rolling window**, complemented by weekly summaries and quarterly reports.

### Getting Stakeholder Agreement

Three parties must agree:

1. **SRE / ops team** — the SLO is defensible without burnout.
2. **Product developers** — they will reduce risk when error budget is exhausted.
3. **Product managers** — the threshold is good enough for users—performance below this value is unacceptably low and worth spending engineering time to fix.

### Error Budget Policy

A written policy that defines what happens when the error budget is exhausted:

- **Production freeze** — halt risky changes.
- **Dev team shifts to reliability** — prioritize reliability bugs, push back on feature requests.
- **Bug prioritization** — top priority to reliability-related bugs from the past 4 weeks.

The policy must be approved by PM, dev team, and SREs. If any party disagrees, iterate on SLIs/SLOs until consensus.

Example: [Example Error Budget Policy](https://sre.google/workbook/error-budget-policy/)

### Documenting SLOs

An SLO document should include:

- Service description, SLO details, SLI implementations
- Rationale behind the numbers (experimental? observational? ad hoc?)
- How the error budget is calculated and consumed
- Authors, reviewers, approvers, approval date, next review date

Example: [Google SRE - SLO Documnets: Game Services API, HTTP, Score.](https://sre.google/workbook/slo-document/#appafn1-marker)

### Continuous Improvement

**Improving SLO quality:**

- Correlate SLI dips with actual outages and support tickets.
- If outages aren't captured by SLIs → improve coverage.
- If SLIs fire without user impact → relax the SLO or change the SLI implementation.

**Levers for improvement:**

1. **Tighten or relax the SLO** based on observed correlation with user happiness.
2. **Change the SLI implementation** — move measurement closer to the user or improve coverage.
3. **Set an aspirational SLO** — track a stricter target alongside the current one, without triggering the error budget policy.

### Decision Making with SLOs and Error Budgets

- Quantify incidents by error budget consumed (e.g. "this outage used 13% of quarterly budget").
- Compare competing reliability projects by their estimated impact on the error budget.
- Use the **SLO decision matrix** to determine action:


| SLO met? | Toil | Customer satisfaction | Action                                                      |
| -------- | ---- | --------------------- | ----------------------------------------------------------- |
| Met      | Low  | High                  | Relax processes / increase velocity, or step back           |
| Met      | Low  | Low                   | Tighten SLO                                                 |
| Met      | High | High                  | Reduce alert noise; if real, loosen SLO temporarily and fix |
| Met      | High | Low                   | Tighten SLO                                                 |
| Missed   | Low  | High                  | Loosen SLO                                                  |
| Missed   | Low  | Low                   | Increase alerting sensitivity                               |
| Missed   | High | High                  | Loosen SLO                                                  |
| Missed   | High | Low                   | Offload toil, fix product, improve automation               |


### Advanced Topics

**Critical User Journeys** — define SLOs around end-to-end user tasks (e.g. "complete a purchase"), not just individual API calls. Requires joining log events or client-side instrumentation.

**Grading Interaction Importance** — bucket requests by tier (premium vs. free) or expected responsiveness (interactive vs. batch download) and apply different SLOs to each.

**Modeling Dependencies** — if a component is a critical dependency, its SLO must be at least as high as the dependent service's SLO. Don't assume independent failure modes when calculating multi-zone availability — shared dependencies break the math.

## Embracing Risk

*[Book, Part II - Principles, Chapter 3](https://sre.google/sre-book/embracing-risk/)*

### Core Premise

Pursuing 100% reliability is the wrong goal. Beyond a certain point, increasing reliability:

- Limits feature development velocity.
- Dramatically increases cost (each incremental "nine" is ~10x more expensive than the last).
- Yields diminishing returns — users on unreliable networks/devices cannot perceive the difference (e.g. a user on a 99% reliable smartphone cannot distinguish 99.99% from 99.999% service reliability).

SRE balances the risk of unavailability against rapid innovation and operational efficiency to optimize **overall user happiness** (features + service + performance).

### Managing Risk

Reliability cost has two dimensions:

1. **Redundant resources** — spare compute, storage parity, failover capacity for maintenance.
2. **Opportunity cost** — engineering time spent on reliability instead of user-visible features.

SRE treats risk as a continuum and performs cost/benefit analysis to place each service at the appropriate point. The availability target is treated as both a **minimum and a maximum** — exceeding it wastes opportunity to ship features, pay down tech debt, or cut operational costs.

### Measuring Service Risk

Risk is made tractable by focusing on **unplanned downtime**, expressed as an availability target in "nines."

**Time-based availability:**

```
availability = uptime / (uptime + downtime)
```

Example: 99.99% availability ≈ 52.56 minutes of downtime per year.

**Aggregate (request-based) availability:**

```
availability = successful requests / total requests
```

Example: 2.5M requests/day at 99.99% target → up to 250 errors allowed per day.

Request-based availability is preferred at Google because globally distributed services are almost always partially up, making uptime-based metrics less meaningful. This metric also applies to non-serving systems (batch, pipeline, storage) by defining "successful units of work."

Targets are typically set **quarterly** and tracked **weekly or daily** to catch meaningful deviations early.

### Risk Tolerance of Consumer Services

Risk tolerance is identified by working with product owners to translate business goals into engineering objectives. Key factors:

**Target level of availability:**

- Consumer vs. enterprise audience
- Competitive landscape — what do competitors offer?
- Free vs. paid service
- Direct revenue impact
- User expectations

Example: Google Apps for Work (enterprise, revenue-critical) → 99.9% external target backed by a stricter internal target and contractual penalties. YouTube (consumer, rapid growth phase) → lower availability target to prioritize feature velocity.

**Types of failures:**

- Constant low error rate vs. occasional full outage may yield the same absolute error count but have different business impact.
- Privacy/trust failures (e.g. exposing private data) may justify taking down the entire service during investigation, even if the alternative is partial degradation.
- Some services accept planned maintenance windows, counted as planned (not unplanned) downtime.

**Cost:**

- For revenue-bearing services, map availability improvements directly to revenue.
- Example: service earning $1M, improving from 99.9% → 99.99% (0.09% improvement) → incremental revenue = $1M × 0.0009 = $900. If engineering cost > $900, the investment is not justified.
- When a direct revenue function is unavailable, compare against ISP background error rates (typically 0.01%–1%).

**Other service metrics:**

- Latency requirements vary by product context. AdWords requires ultra-low latency (must not slow Search). AdSense has a looser latency goal (must not slow the publisher's page), enabling cheaper provisioning with fewer geographical locations.
- Understanding which metrics matter and which don't provides degrees of freedom for taking thoughtful risks.

### Risk Tolerance of Infrastructure Services

Infrastructure differs from consumer services because it has **multiple clients with varying needs**.

**Target level of availability:**

- Example: Bigtable serves both low-latency user-facing paths (need high reliability, short queues) and offline batch analysis (need high throughput, queues always full). These needs are antithetical.

**Partitioning by service level:**

- Offer infrastructure at **multiple explicit levels of service** rather than engineering everything to be ultra-reliable (which is too expensive at scale).
- Example: Bigtable low-latency clusters (high redundancy, slack capacity, higher cost) vs. throughput clusters (run hot, less redundancy, 10–50% of cost).
- Clients choose the level that meets their needs at the lowest cost.
- Different guarantees can run on **identical hardware/software** — differentiated by resource quantities, redundancy, geographic constraints, and configuration.

**Frontend infrastructure:**

- Reverse proxy / load balancing systems at the network edge must be engineered for extremely high reliability — if a request never reaches the application server, it is lost with no fallback.

### Motivation for Error Budgets

Product development and SRE teams are evaluated on different metrics:

- **Product development** → product velocity → incentive to push fast.
- **SRE** → service reliability → incentive to resist change.

Common tension areas:

| Area | Trade-off |
| --- | --- |
| Software fault tolerance | Too little → brittle; too much → product nobody uses |
| Testing | Too little → outages/leaks; too much → missed market |
| Push frequency | Every push carries risk |
| Canary duration & size | Longer/larger = safer but slower |

Informal balances are often a function of negotiating skill rather than data. The goal is an **objective, data-driven metric** agreed upon by both sides.

### Forming the Error Budget

Process:

1. **Product Management** defines an SLO (expected uptime per quarter).
2. The **error budget** = 100% − SLO (the allowed unreliability for the quarter).
3. **Actual uptime** is measured by a neutral third party (the monitoring system).
4. As long as measured uptime is above the SLO (budget remaining), new releases can proceed.

Example: SLO = 99.999% → error budget = 0.001%. A problem that fails 0.0002% of queries spends 20% of the quarterly budget.

### Benefits of Error Budgets

- Provides a **common incentive** for both teams to balance innovation and reliability.
- **Self-policing velocity:** when budget is large, developers take more risks; when budget is nearly drained, developers themselves push for more testing or slower releases.
- **Infrastructure failures count too:** network outages and datacenter failures consume the same budget, reducing remaining pushes for the quarter. The entire team shares responsibility.
- **Highlights cost of over-reliability:** if the team cannot launch features fast enough, they may elect to loosen the SLO (increase the budget) to accelerate innovation.
- More nuanced than a simple on/off release gate — teams can slow down releases or roll back proactively as the budget approaches exhaustion.
